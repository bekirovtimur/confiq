# Правила работы с Confiq

## Карта проекта

- `app.py` — создание Flask-приложения, регистрация blueprint, инициализация рабочей БД и стартовых данных.
- `models.py` — SQLAlchemy-модели `User`, `Config`, `ConfigType`, `Endpoint`, `Group` и таблицы связей.
- `auth.py` — вход и выход; `routes/user.py` — пользовательские маршруты; `routes/admin.py` — административные.
- `templates/` — Jinja2-интерфейс; `static/css/style.css` и `static/js/app.js` — собственные стили и JavaScript в стиле Material Design.
- `static/js/app.js::ConfigMenuController` — общий обработчик меню карточек в `templates/user/dashboard.html` и `templates/user/configs.html`; стили — `.config-menu` в `static/css/style.css`.
- `utils/qr.py` — общая политика вместимости и построения QR.
- `warp/client.py` — интеграция с Cloudflare; `data/initial_config_types.py` — стартовые шаблоны типов.
- `migrations/` — самостоятельные скрипты миграций. Не запускайте их на рабочей БД без явного согласования.
- `tests/` — тесты `unittest`; `docs/` — документация пользователя и развёртывания.

## Проверки и безопасная работа с данными

Из корня репозитория:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -B -m unittest discover -s tests -v
git diff --check
```

Можно использовать уже подготовленное виртуальное окружение. Не добавляйте окружение и сгенерированный байткод в изменения. `-B` отключает запись байткода при запуске тестов; установка зависимостей всё равно может создавать файлы внутри окружения.

**Не импортируйте `app.py` в тестах или для безобидной проверки импорта.** На уровне модуля создаётся приложение: фабрика работает с `/data/warp_manager.db`, создаёт таблицы и стартовые записи. В тестах создавайте отдельное `Flask`-приложение, регистрируйте нужные blueprint и используйте `sqlite://`, как в существующих тестах маршрутов.

- Не читайте и не меняйте реальные `data/warp_manager.db`, `/data`, `.env`, ключи и токены ради тестов.
- Используйте синтетические секреты и моки Cloudflare API. Реальные создание/удаление устройств и проверка VPN-подключения не входят в модульные тесты.
- Не выводите содержимое конфигов, приватные ключи, токены и QR в логи или сообщения об ошибках.
- Учитывайте существующие изменения пользователя; не откатывайте их при очистке артефактов проверок.

## Границы доступа

- Маршруты `/user/configs/<id>` и действия просмотра, скачивания, QR, редактирования и удаления проверяют `user_id=current_user.id`. Не ослабляйте эту проверку ради административных функций.
- Доступ к конфигурациям любого владельца находится отдельно в `/admin/configs/<id>` и защищён **обоими** декораторами: `login_required` и `admin_required`.
- Проверка доступа должна происходить до чтения/обработки содержимого и построения QR.
- В `routes/user.py` функции `render_config_page`, `download_config_response`, `config_qr_response` — общие помощники для уже авторизованной конфигурации. Они сами не проверяют права; проверка — обязанность вызывающего маршрута.
- `admin_view` в шаблоне выбирает административные ссылки и действия, но не заменяет серверную авторизацию. Не добавляйте несуществующие действия удаления/переименования чужих конфигов в этот интерфейс.
- Изменяющие формы должны проходить серверную валидацию и CSRF-проверку `FlaskForm`. Не отключайте CSRF в рабочем приложении.

## Инварианты смены типа конфигурации

Реализация: `routes/admin.py::change_config_type`; форма: `templates/admin/change_config_type.html`.

- Целевой тип активен, привязан к текущему endpoint и отличается от текущего. Ограничение проверяется сервером через допустимые choices формы.
- Новый файл строится из сохранённых данных по шаблону Jinja2 с `StrictUndefined`. Контекст включает ключи, IP-адреса, `endpoint`, `port`, `cloudflare_id` и `token`; неизвестные переменные и пустой результат не допускаются.
- В одной транзакции обновляются только `config_type_id` и `config_content`. ID, название, владелец, endpoint, дата создания, ключи, IP и реквизиты Cloudflare не меняются.
- Не вызывайте Cloudflare API и не создавайте новое устройство или запись `Config` при смене типа.
- Ошибка генерации или commit должна оставлять исходный конфиг без изменений: нужен rollback.
- Старые скачанные файлы не отзываются. Пользователю требуется повторный импорт; доступность типа на endpoint не доказывает совместимость протокола с сервером.
- Текущая функция не требует миграции схемы. Не добавляйте миграции без изменения моделей.

## Удаление типов и стартовая инициализация

Реализация: `routes/admin.py::config_types`, `delete_config_type`, `toggle_config_type`; список: `templates/admin/config_types.html`.

- Счётчик использования учитывает конфиги всех владельцев, в том числе для отключённых типов. Используйте агрегированный запрос, не загружайте содержимое конфигов и не делайте отдельный запрос для каждой строки.
- Удаление разрешено только при отсутствии конфигураций этого типа. Недоступная кнопка в интерфейсе не заменяет серверную проверку при POST.
- Сохраняйте условие отсутствия связанных конфигов в самом SQL DELETE (`~ConfigType.configs.any()`), помимо предварительного подсчёта. Не заменяйте его безусловным ORM-удалением, которое может обнулить `config_type_id` у связанных конфигураций.
- Привязки к endpoints не блокируют удаление неиспользуемого типа: очищаются только связи и сам тип в одной транзакции. Endpoints, другие типы и существующие конфиги не удаляются и не изменяются; Cloudflare API не вызывается.
- При ошибке записи или отказе условного DELETE нужен rollback, включая восстановление привязок. Не раскрывайте текст исключения в пользовательском сообщении.
- Удаление и переключение активности — только POST с `login_required`, `admin_required` и валидацией `ConfigTypeActionForm`, включая CSRF. В списке обе формы получают токен через `action_form.hidden_tag()`.
- В `app.py` наличие таблицы `config_types` проверяется **до** `db.create_all()`. Стандартные шаблоны добавляются только при первоначальном создании таблицы. Не возвращайте восстановление отсутствующих типов при каждом запуске: удалённые типы должны оставаться удалёнными, даже если таблица пуста.
- Существующая стартовая привязка WireGuard к endpoints без типов остаётся отдельным поведением. Если WireGuard сохранён, он может быть назначен таким endpoints при перезапуске; это не восстановление удалённых типов.
- Эти изменения не требуют миграции схемы.

## Выбор endpoint при создании конфигурации

Реализация: `routes/user.py::create_config`; проверки: `tests/test_user_config_creation.py`.

- Сначала определяйте доступные endpoints, затем сортируйте общий результат по `(ep.name.casefold(), ep.id)` до заполнения choices и выбора первого endpoint для типов по умолчанию. Так сохраняются сортировка без учёта регистра, поддержка кириллицы и стабильный порядок при одинаковых названиях.
- Сортировка применяется и к общему списку, и к endpoints группы; не меняйте глобальный порядок relationship ради одного выпадающего списка.
- Не расширяйте доступ сортировкой. Существующий режим совместимости сохраняется: пользователь без группы или группа без endpoints видят все endpoints.
- Явный выбор через `?endpoint_id=...` или POST не должен сбрасываться из-за сортировки. Проверки доступности endpoint и поддержки выбранного типа остаются серверными.

## Меню карточек конфигураций

- Используйте общий `ConfigMenuController` для дашборда и пользовательского списка. Не возвращайте дублирующие `toggleConfigMenu` и обработчики закрытия в шаблонах.
- Кнопка связана с меню через `data-config-menu` и `aria-controls`; `aria-expanded` отражает состояние. Само меню имеет классы `md-menu config-menu` и уникальный ID `configMenu<id>`.
- При открытии меню временно переносится в `document.body`, при закрытии возвращается в исходного родителя. Это обходит `overflow: hidden` и контексты наложения карточек; одного увеличения `z-index` недостаточно. Не меняйте глобальный overflow всех `.md-card` ради меню.
- Позиционирование — `fixed`, с привязкой к кнопке, учётом размеров меню и видимой области (`visualViewport`, если доступен). Меню выбирает открытие вверх/вниз, удерживается по горизонтали в пределах экрана и оставляет отступы от его краёв.
- Если меню целиком не помещается, ограничивайте высоту доступным пространством и разрешайте внутреннюю прокрутку. Прокрутка самого меню не должна закрывать его; прокрутка страницы или внешнего контейнера — должна.
- Одновременно открыто только одно меню конфигурации. Повторное нажатие кнопки, выбор действия, клик снаружи, Escape и изменение размера окна закрывают его. Escape возвращает фокус на кнопку.
- Не вмешивайтесь в обработчик меню пользователя в шапке. Сохраняйте действия просмотра, редактирования, скачивания и удаления, условную доступность QR и серверную проверку владельца.

## QR и повторное использование интерфейса

- Используйте `utils/qr.py::prepare_qr`, не создавайте независимые генераторы. Максимальная версия — `15`, коррекция — `M`, белое поле — `4` клетки.
- Для недоступного QR просмотр и скачивание должны работать; прямой QR-маршрут возвращает HTML `422` с причиной и рабочей ссылкой на скачивание.
- PNG-ответы содержат `Cache-Control: private, no-store`. Нельзя изменять текст конфигурации ради вместимости QR.
- В пользовательских списках проверяйте QR только для отображаемых конфигураций, без создания PNG.
- Общие шаблоны просмотра и недоступного QR находятся в `templates/user/` и обслуживают также администратора. В административном режиме ссылки должны оставаться в `/admin/configs/...`.

## Тесты и документация

- `tests/test_admin_configs.py` — права, общий список, административные действия, безопасная смена типа, счётчики и удаление типов, CSRF и откат привязок при ошибках.
- `tests/test_qr.py` — вместимость, плотность, PNG и сохранение исходного текста.
- `tests/test_qr_routes.py` — пользовательские страницы, доступ к QR, проверка владельца и подключение общего обработчика меню в обоих шаблонах.
- `tests/test_user_config_creation.py` — сортировка endpoints, ограничения групп, режим совместимости для пустой группы, типы первого endpoint и сохранение явного выбора.
- `tests/test_config_menus_browser.py` — необязательные браузерные проверки через Playwright и Chromium: границы экрана, открытие вверх/вниз, меню с QR и без него, внутренняя прокрутка, доступность удаления и закрытие меню. Используется изолированный Flask test client без рабочего сервера; внешние HTTP-запросы блокируются.
- Для браузерных проверок установите Playwright только в тестовое окружение: `.venv/bin/python -m pip install playwright`; при отсутствии системного Google Chrome/Chromium — `.venv/bin/python -m playwright install chromium`. Запуск: `.venv/bin/python -B -m unittest discover -s tests -p test_config_menus_browser.py -v`. Без Playwright или браузера проверки пропускаются: явно отличайте пропуск от успешного браузерного прогона. Не добавляйте Playwright в рабочие зависимости ради этих тестов.
- При изменении доступа, шаблонов или маршрутов добавляйте регрессионные тесты. Сохраняйте рабочую БД изолированной от тестов.
- Синхронизируйте `README.md`, `docs/ADMIN_CONFIGS.md` и при необходимости `docs/DEPLOYMENT.md` с изменениями поведения. `docs/QR_CODE_FIX_PLAN.md` содержит текущую реализацию и явно помеченный исторический план, а не список невыполненных задач.
- Не утверждайте, что тесты доказывают реальную совместимость VPN-клиента/сервера или сканирование камерой: это отдельные ручные проверки.
