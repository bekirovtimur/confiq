# Управление конфигурациями администратором

## Общий список

После входа с правами администратора выберите **Все конфигурации** в верхнем меню или **Все конфиги** в мобильном меню. Также ссылка доступна в панели администратора. Адрес страницы — `/admin/configs`.

Таблица содержит ID, название, владельца, тип, endpoint с адресом и дату создания. На странице отображаются 10 конфигураций, сначала новые; при одинаковой дате — по убыванию ID. Переход между страницами: `?page=2`, `?page=3` и т. д.

Действия в строке:

- **Просмотреть** — содержимое, сведения о подключении, владелец, инструкции для выбранного типа и QR-код, если он доступен.
- **Скачать** — сохранённый текст конфигурации без изменений. Если название типа содержит `clash` без учёта регистра, расширение — `.yaml`, иначе — `.conf`.
- **Изменить тип** — открыть форму выбора нового шаблона.

Ссылки на конфигурации со страниц endpoint и редактирования пользователя также открывают административный просмотр. Он не предоставляет новых действий удаления или переименования чужого конфига; массовые операции с endpoint остаются отдельными существующими сценариями.

## Смена типа

1. В общем списке или на странице просмотра нажмите **Изменить тип**.
2. Проверьте владельца, текущий тип и endpoint.
3. Выберите новый тип и подтвердите изменение кнопкой **Изменить тип**.
4. Скачайте обновлённый файл и импортируйте его в подходящий клиент.

В списке выбора доступны только типы, которые:

- активны (`ConfigType.is_active`);
- привязаны к текущему endpoint через `Endpoint.config_types`;
- отличаются от текущего типа.

Эти ограничения проверяются сервером, в том числе при ручной отправке POST. Если других подходящих типов нет, форма сообщает об этом и не предлагает сохранение. У старых конфигураций без указанного типа можно выбрать любой подходящий активный тип текущего endpoint.

### Какие данные меняются

Операция обновляет только `Config.config_type_id` и `Config.config_content` в одной транзакции. Сохраняются ID, название, владелец, endpoint, дата создания, ключи, адреса клиента и реквизиты устройства Cloudflare. Запросы создания или удаления устройства в Cloudflare не выполняются; новая конфигурация в БД не создаётся.

Для существующих установок с актуальной схемой `Config` новая миграция БД не нужна. Исторические миграции для более старых установок остаются необходимыми, если их схема ещё не обновлена.

### Переменные шаблона

Новый файл формируется из `ConfigType.config_template` с помощью Jinja2:

| Переменная | Источник |
| --- | --- |
| `private_key` | Приватный ключ клиента |
| `public_key` | Публичный ключ клиента |
| `peer_public_key` | Публичный ключ сервера |
| `client_ipv4`, `client_ipv6` | Сохранённые IP-адреса клиента |
| `endpoint` | Адрес текущего endpoint |
| `port` | Порт текущего endpoint |
| `cloudflare_id` | ID существующего устройства Cloudflare |
| `token` | Токен существующего устройства Cloudflare |

Для смены типа включён `StrictUndefined`: неизвестная переменная считается ошибкой, а не заменяется пустой строкой. Ошибка синтаксиса, пустой результат или ошибка записи в БД отменяют изменение. Интерфейс сообщает, что исходный конфиг сохранён, не раскрывая детали ошибок с потенциальными секретами.

Изменение самого шаблона в разделе **Типы** не перегенерирует уже сохранённые конфиги автоматически. Форма смены типа исключает текущий тип и не является кнопкой обновления по тому же шаблону.

### Ограничения

- Привязка типа к endpoint — настройка доступности, а не автоматическая проверка поддержки протокола сервером. Например, совместимость параметров AmneziaWG нужно проверять отдельно.
- Успешная генерация Jinja2 не подтверждает корректность синтаксиса файла для VPN-клиента и работоспособность подключения.
- Старые скачанные файлы не обновляются и не отзываются. Ключи устройства сохраняются: смена типа не является ротацией ключей или отзывом доступа.
- Вместимость QR проверяется по новому содержимому. Большой файл может не иметь доступного QR; используйте скачивание и импорт. См. [политику QR-кодов](QR_CODE_FIX_PLAN.md).

## Доступ и маршруты

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/admin/configs` | Список всех конфигураций |
| GET | `/admin/configs/<id>` | Просмотр |
| GET | `/admin/configs/<id>/download` | Скачивание |
| GET | `/admin/configs/<id>/qr` | PNG или HTML с причиной недоступности и кодом `422` |
| GET/POST | `/admin/configs/<id>/change-type` | Форма и сохранение нового типа |

Это маршруты веб-интерфейса с сессионной аутентификацией. Все требуют `login_required` и `admin_required`. POST смены типа проходит валидацию `FlaskForm`, включая CSRF. При отсутствии входа или прав администратора запрос перенаправляется на страницу входа; при отсутствии конфигурации авторизованный администратор получает `404`.

Обработчики `/user/configs/<id>` и их действия по-прежнему доступны только владельцу, даже если текущий пользователь — администратор. Обычный пользователь не получает доступ к чужому конфигу через административные маршруты.

## Проверка после обновления

1. Под администратором откройте общий список и конфигурацию другого пользователя.
2. Проверьте скачивание и QR (либо сообщение о недоступности и ссылку на файл).
3. Смените тип на другой активный тип текущего endpoint.
4. Проверьте новое содержимое и расширение файла; убедитесь, что владелец, endpoint и ключи сохранились.
5. Войдите владельцем: на его странице и при скачивании должен быть новый файл.
6. Под другим обычным пользователем проверьте, что чужая конфигурация недоступна.
7. Проверьте импорт и подключение в целевом клиенте. Автоматические тесты не проверяют реальное соединение с VPN-сервером.

Автоматические сценарии находятся в `tests/test_admin_configs.py`: доступ и навигация, стабильная пагинация, просмотр/скачивание/QR, выбор допустимых типов, сохранение исходных данных, откат ошибок шаблона и БД, CSRF, старые конфиги без типа. Тесты используют SQLite в памяти, синтетические ключи и запрещают обращения к `WarpAPI.create_config` и `WarpAPI.delete_config`.
